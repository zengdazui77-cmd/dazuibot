# Isolated team code executor

This is a separate control-plane service for approved team code tasks. The team API signs a task envelope without a model key, Git token, session token, or local path. The controller creates one short-lived Kubernetes Job per envelope and keeps the API lease alive. The Job receives only the task envelope and a task-scoped capability; it can read a bounded repository archive and call the model proxy for that task. The team API remains the only component that holds encrypted team credentials.

The runner image installs DSH dependencies from the locked `dsh-runtime/package-lock.json` inside the Linux image build, so it does not reuse the desktop machine's platform-specific `node_modules`. Build it from the repository root with `docker build -f team-service/executor/Dockerfile .`; the Docker build checks the Linux DSH SDK import and runner syntax. Build the controller from the repository root with `docker build -f team-service/executor/Dockerfile.control .`; it compiles from source inside a multi-stage build and does not depend on ignored host `dist` output. Pin both images by digest in `deploy/kubernetes.yaml`. The Kubernetes cluster must enforce NetworkPolicy. The controller lives in `dazuibot-tasks`, separately from the team API in `dazuibot-team`; the API Deployment must carry the label `app.kubernetes.io/name=dazuibot-team-api` and listen on port 8787 inside that namespace. The controller policy accepts ingress only from that API label. Per-task policies deny all ingress and permit egress only to the team API and cluster DNS.

This manifest does not deploy the team API or PostgreSQL. The current team API scaffold uses Docker Compose, so deploying it unchanged does not create the Kubernetes Service and labeled API Pods assumed by this executor manifest. Before enabling code tasks, deploy the API and database in the chosen environment, then verify the API Service name, labels, port, `TEAM_CODE_EXECUTOR_BROKER_URL`, `TEAM_API_URL`, `EXECUTOR_API_URL`, and NetworkPolicy rules agree. The sample uses private-cluster HTTP URLs; production must protect these service-to-service requests with TLS/mTLS or an explicitly trusted and isolated cluster network. Do not treat parsing the YAML as deployment validation.

Required production settings are `TEAM_API_URL`, `TEAM_CODE_EXECUTOR_SECRET`, `EXECUTOR_NAMESPACE`, and a digest-pinned `EXECUTOR_RUNNER_IMAGE`. `TEAM_API_URL` is the private Kubernetes service origin reachable from runner Jobs; it must match the API `TEAM_CODE_EXECUTOR_BROKER_URL` value. `EXECUTOR_API_URL` is the same private service origin used by the controller for heartbeats and callbacks. The shared executor secret is mounted only in the controller Deployment, never in a task Job. Use a distinct random value from the API session and credential secrets.

The controller is deliberately single-replica in the starter manifest. Kubernetes Job names and payload signatures make dispatch idempotent, while the API lease and monotonically increasing heartbeat sequence prevent stale controllers from publishing results. Before production use, validate the cluster's NetworkPolicy enforcement, Pod Security admission, image signature policy, DNS/TLS path to the API, cancellation behavior, and restore the API database from backup in a staging cluster.
